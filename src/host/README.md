# src/host

## Overview

`src/host` holds the per-session host and the CLI-side code that starts, reaches and cleans up hosts. `lifecycle.ts` allocates a session, spawns a detached host process and destroys, lists or reconciles sessions. `manifestWriter.ts` orders the host's manifest writes. `programGroup.ts` records the program's session token in `program.json` and decides before each kill of the program's process group whether the group is still the program's. `hostMain.ts` is the host process: it spawns the PTY, appends all eleven event types (`output`, `input_text`, `input_paste`, `input_keys`, `input_mouse`, `input_run`, `run_complete`, `resize`, `signal`, `exit` and `marker`) to `events.jsonl` through `EventLog`, serves RPC on a Unix socket and renders through `HostRendererManager`. `replaySlices.ts` replays a long log to a renderer backend in slices, so that a slow replay shows progress. `mouseRpc.ts` serves the `mouse` RPC, and `mouseInput.ts` stages its held-button state. `runCompletionCoordinator.ts` and `runCompletionSentinel.ts` detect when a command sent with `run` has finished. The host is an internal detail. The CLI JSON envelope in `src/protocol/` is the stable surface.

## Interface

- `runHost(sessionId, creatorPid)` is the host process entry point. It waits for the first manifest with `waitForManifestFromCreate`, then registers RPC handlers for `inspect`, `snapshot`, `screenshot`, `type`, `mark`, `paste`, `run`, `sendKeys`, `mouse`, `resize`, `signal`, `wait`, `waitForRender` and `destroy`. [hostMain.ts:runHost]
- `waitForManifestFromCreate(path, creatorPid)` returns the manifest at `path`. It polls every 20 ms while the manifest is missing and the creator process is alive. When the creator exits before the manifest appears, it throws `SESSION_NOT_FOUND`. [hostMain.ts:waitForManifestFromCreate]
- `normalizeExitSignal(signal)` maps a PTY exit signal number to a string, or `null` for `null` and 0. [hostMain.ts:normalizeExitSignal]
- `isSessionCommandable(state)` and `assertSessionCommandable(state)` check that the session status is commandable. The assert throws `SESSION_NOT_RUNNING`. [hostMain.ts:isSessionCommandable] [hostMain.ts:assertSessionCommandable]
- `resolveHostRendererName(input?)` picks the renderer name from the input, then `AGENT_TTY_HOST_RENDERER`, then `AGENT_TTY_RENDERER`, then `DEFAULT_RENDERER_NAME` (from `src/renderer/names.ts`). It throws `INVALID_INPUT` for an unknown renderer name. [hostMain.ts:resolveHostRendererName]
- `MAX_CONSECUTIVE_POLL_FAILURES` (10) is the number of failed polls in a row after which a `waitForRender` wait rejects with the last poll error. A `CliError` keeps its code. The RPC server sends any other error as an RPC error, which the CLI reports as `RPC_ERROR`. [hostMain.ts:MAX_CONSECUTIVE_POLL_FAILURES]
- `allocateSession(config, launch)` validates an `AllocateConfig`, creates the session directory, calls `launch(sessionId)`, writes `host.json` for the launched host when `captureHost` can read it, and writes the first `running` manifest with the returned PID as `hostPid`. It returns an `AllocateResult` with `sessionId` and `sessionDirectory`. [lifecycle.ts:allocateSession] [lifecycle.ts:AllocateConfig] [lifecycle.ts:AllocateResult]
- `launchHost(config)` spawns the host process for a `LaunchHostConfig` and returns a `LaunchedHost`: its PID and a `stop()` that sends the host SIGTERM through the `ChildProcess` handle, and nothing once the host has exited. `create` calls it from the `launch` callback of `allocateSession`, and calls `stop()` on any error after `allocateSession` returned, such as a give-up on the host. [lifecycle.ts:launchHost] [lifecycle.ts:LaunchHostConfig] [lifecycle.ts:LaunchedHost] [src/cli/commands/create.ts:runCreateCommand]
- `removeSocketDirectoryIfEmpty(socketFile)` removes the Home's socket directory with `rmdir`. A directory that still holds a socket (`ENOTEMPTY` or `EEXIST`) or is already gone (`ENOENT`) stays as it is. `destroySession` and `reconcileSession` call it after they unlink a socket. The host's shutdown and `doctor`'s socket check call `removeSocketDirectoryBestEffort`, which logs any other `rmdir` error at debug level instead of throwing it. [lifecycle.ts:removeSocketDirectoryIfEmpty] [lifecycle.ts:removeSocketDirectoryBestEffort]
- `ensureSocketRoot(root = socketRootDirectory())` creates the socket root with `mkdir` mode `0o700` and then `chmod 0o700` when it is missing. It throws `STORAGE_WRITE_ERROR`, with the path, the owner's uid and the mode in `details`, unless `lstat` shows a directory of the caller's uid with no group or other mode bit: a symlink, a file, a directory of another uid or a group or other bit fails. A private root without all owner bits, as another `create` shows it while umask took them and its `chmod` is pending, gets `chmod 0o700`. It does nothing where `process.getuid` is missing (Windows). `create` calls it before it allocates a session, because the host's errors reach nobody. [socketRoot.ts:ensureSocketRoot]
- `socketRootExists(root = socketRootDirectory())` returns `false` for a missing root and `true` for a private one (a directory of the caller's uid with no group or other bit), after the same `chmod 0o700` of a private root without all owner bits. It throws the same `STORAGE_WRITE_ERROR` for any other root. [socketRoot.ts:socketRootExists]
- `isOwnLegacySocket(socketFile)` is true when `lstat` shows a socket of the caller's uid, in a Home folder of that uid that no group or other user can write, under a root of that uid or of root that no group or other user can write or that has the sticky bit. No other user can then rename or replace a folder on the path before the connect. [socketRoot.ts:isOwnLegacySocket]
- `removeDeadHostSocket(sessionDirectory, manifest)` unlinks the session's socket and removes the Home's socket directory if it is empty, when the manifest names no host pid or `judgeHost` reads the host as dead. It also removes the socket at `legacySocketPath` when `isOwnLegacySocket` accepts it. When the host check throws, it removes neither socket. It logs errors instead of throwing them. `gc` calls it before it removes a session folder, and `destroySession` calls it before it throws `SESSION_ALREADY_DESTROYED`. [lifecycle.ts:removeDeadHostSocket]
- `listenInSocketDirectory(socketFile, listen)` calls `ensureSocketRoot`, then runs `mkdir`, `chmod 0o700` and `listen` up to 5 times when the socket directory vanished before the `chmod` or the bind, because a teardown in the same Home removed it. libuv reports such a bind as `EACCES`. The host and `doctor`'s socket check use it. [lifecycle.ts:listenInSocketDirectory]
- `isProcessAlive(pid)` returns `false` for `null` and for a PID that `process.kill(pid, 0)` reports as `ESRCH`, and `true` when the probe succeeds. It asserts a positive integer PID and rethrows other errors, such as `EPERM`. [lifecycle.ts:isProcessAlive]
- `destroySession(sessionId, force?, options?)` destroys a session and waits until its manifest shows a terminal status. `DestroySessionOptions` has an optional `AbortSignal`. [lifecycle.ts:destroySession] [lifecycle.ts:DestroySessionOptions]
- `listSessions(home, all?)` returns `SessionSummary[]`. It reconciles active sessions, and ended sessions other than destroyed whose folder holds the destroy marker, first. It hides terminal sessions unless `all` is true. A missing `<home>/sessions` gives `[]`, and any other read error throws `STORAGE_READ_ERROR`. [lifecycle.ts:listSessions] [lifecycle.ts:SessionSummary]
- `reconcileSession(sessionDirectory)` moves a non-terminal session to a terminal status when its host process is gone. [lifecycle.ts:reconcileSession]
- `captureProgram(pid)` returns a `ProgramRecord` (`version`, `pid`, `bootId`, `autogroup`) for the program that the host just spawned, and `writeProgramRecord(sessionDirectory, record)` writes it to `program.json`. `bootId` is a string and `autogroup` a number, or both are `null`. [programGroup.ts:captureProgram] [programGroup.ts:writeProgramRecord]
- `readProvenProgramGroup(sessionDirectory)` returns the `program.json` record when it has a token and `sharesHostPids` reads true, the unshared group (below) when it has a token and `sharesHostPids` reads false, else `null`. `readProgramGroup(sessionDirectory, childPid)` returns the same for a record with a token, else `{ childPid, sessionDirectory }`, or `null` when `childPid` is `null` or, on Linux, when `host.json` names another pid namespace or machine id than the CLI's (`sharesHostPids`). For a record with a token where `sharesHostPids` reads false, which includes a missing `host.json`, a CLI that cannot read `/proc/self/ns/pid` and a CLI whose `/proc/self` does not name its own pid, both return the unshared group `{ unshared: true }`: no scan or probe of this process shows the program's processes, so `isProgramGroupAlive` reads it alive and `stopProgramGroup` sends it nothing. A `program.json` that does not validate reads as `null` in both, so it gets no kill and no throw. [programGroup.ts:readProgramRecord] [programGroup.ts:readProvenProgramGroup] [programGroup.ts:readProgramGroup] [hostRecord.ts:sharesHostPids]
- `stopProgramGroup(group)` SIGKILLs the group when the record proves it. A group that no scan shows, or whose member ends between two reads (its stat and its autogroup, or the witness and its re-read), gets SIGSTOP and another judgement, at each of up to 5 judgements while `/proc/self` names this process's pid, and SIGCONT when it gets no kill. A group that shows a member that job control or a tracer stopped gets no SIGSTOP before its first freeze, so the SIGCONT cannot resume that member. Each SIGSTOP is followed by a synchronous wait of `STOP_SETTLE_MS` (1 ms), because the stop takes effect only when the kernel next runs a member. `isProgramGroupAlive(group)` reports whether the group still holds a process that the kill would target. When its probe `kill(-pgid, 0)` finds the group but no scan shows a member, live or zombie, `isProcessGroupAlive` probes again: a group whose processes were reaped meanwhile reads ended, and one that still holds the id, such as a fork chain that a freeze missed, reads alive. Scans that show only zombies read the group ended. `judgeProgramGroup(record, bootId, rows)` is the pure decision: `owned`, `gone`, `unproven` or `unknown`. `parseProcStat` and `parseAutogroup` parse `/proc/<pid>/stat` and `/proc/<pid>/autogroup`. `parseAutogroup` returns `null` for text that names no autogroup, and a member whose autogroup file cannot be read or parsed carries no token. [programGroup.ts:stopProgramGroup] [programGroup.ts:isProgramGroupAlive] [programGroup.ts:judgeProgramGroup] [programGroup.ts:parseProcStat]
- `captureHost(pid)` returns a `HostRecord` (`version`, `pid`, `bootId`, `startTicks`, `pidNamespace`, `timeNamespace`, `machineId`) on Linux when `/proc` shows the process and the boot id, else `null`. `machineId` is the first of `/etc/machine-id` and `/var/lib/dbus/machine-id` that holds 32 hex characters, else `null`. A record without `timeNamespace` and `machineId`, which a build between #260 and #267 wrote, still reads, and only the checks of those two fields are skipped. `writeHostRecord(sessionDirectory, record)` writes it as `host.json`, and `readHostRecord(sessionDirectory)` returns it, or `null` when it is missing or unreadable. `hostRecordError(sessionDirectory)` returns the error when the file exists but its read or its check fails, else `null`, so that the `HOST_TIMEOUT` of `destroySession` for an unshared group names `host.json` and that error instead of another pid namespace, and says to make the file readable only for EACCES or EPERM. `judgeHost(pid, record)` returns `dead` only when no process has the pid, a zombie has it, or the record names another boot id or start time, `alive` when both match, and `unknown` otherwise: also off Linux for a pid that exists, for a CLI in another pid namespace or on another machine than the record names, and, instead of a start time mismatch, for a CLI in another time namespace. [hostRecord.ts:captureHost] [hostRecord.ts:writeHostRecord] [hostRecord.ts:readHostRecord] [hostRecord.ts:hostRecordError] [hostRecord.ts:judgeHost]
- `SessionState` holds the host's in-memory `SessionRecord` (type from `src/protocol/schemas.ts`). Methods: `snapshot`, `setChildPid`, `setDimensions`, `setFailureOrigin`, `requestDestroy`, `recordDestroyed` and `recordExit`. [sessionState.ts:SessionState]
- `createSerialManifestWriter(path, snapshot, write?)` returns a function that writes `snapshot()` to `path`. The default `write` is `writeManifest` (`src/storage/manifests.ts`). `runHost` sends every manifest write through one such function. [manifestWriter.ts:createSerialManifestWriter] [hostMain.ts:runHost]
- `EventLog` is the append-only JSONL event log with an in-memory buffer. Methods: `static open(filePath, options?)`, `append(type, payload)` (returns the `seq` of the stored record), `startAppend('input_run', payload)` (returns `{ seq, written }` without an `await`), `getEvents`, `getEventsSince(afterSeq)`, `readAll` and `close`. [eventLog.ts:EventLog]
- `MAX_EVENT_BUFFER_ENTRIES` is 250,000. `EVENT_LOG_TAIL_RESERVE_BYTES` is 4,096. `EVENT_LOG_TAIL_RESERVE_ENTRIES` is 2. `EVENT_LOG_LIMIT_LABEL_PREFIX` starts the label of the stop marker. `statEventLogBytes(filePath)` returns the file size or `undefined` when the file does not exist. `countEventLogEntries(filePath)` counts non-blank lines. [eventLog.ts:MAX_EVENT_BUFFER_ENTRIES] [eventLog.ts:EVENT_LOG_TAIL_RESERVE_BYTES] [eventLog.ts:EVENT_LOG_TAIL_RESERVE_ENTRIES] [eventLog.ts:EVENT_LOG_LIMIT_LABEL_PREFIX] [eventLog.ts:statEventLogBytes] [eventLog.ts:countEventLogEntries]
- `createMouseRpcHandler(deps)` returns the `mouse` handler `(request, rendererName)`, which resolves a `MouseResult` (`reported`, `bytesWritten`, `seq`). `MouseRpcDependencies` injects the renderer manager (in `runHost` a second `HostRendererManager` that only mouse input uses, so a render on another renderer or profile never replaces the encoder's backend and its same-cell motion state), the profile, the libghostty-vt probe, the replay loader, the commandable check, the PTY writer and the `input_mouse` append. The handler keeps the held buttons between requests. [mouseRpc.ts:createMouseRpcHandler] [mouseRpc.ts:MouseRpcDependencies]
- `prepareHeldMouseButtons(currentHeld, input)` returns the next held set, `anyButtonPressed` and the `dragButton` that a button-free `move` reports, without changing `currentHeld`. [mouseInput.ts:prepareHeldMouseButtons]
- `buildReplayInput(sessionId, manifest, events, ...)` builds a validated `ReplayInput` (type from `src/renderer/types.ts`) with the initial size and target sequence number. [replay.ts:buildReplayInput]
- `RpcServer(socketPath, handlers)` serves newline-delimited JSON RPC on a Unix socket, one request per connection, with `listen()` and `close()`. `MethodHandler` and `MethodContext` type the handlers. `MethodContext.signal` aborts when the client socket closes. `MethodContext.keepAlive()` writes one space ahead of the response line, which tells the client that the handler still makes progress, and does nothing once the client has gone or the response is sent. [rpcServer.ts:RpcServer] [rpcServer.ts:MethodHandler] [rpcServer.ts:MethodContext]
- `sendRpc(socketPath, method, params?, timeoutMs?, signal?)` sends one request to a host and returns the validated result. For a path under the socket root, it connects only after `socketRootExists` read the root as private, so no other user can have put the socket there. When the root is missing or not private, or the socket is missing (`HOST_UNREACHABLE` with errno `ENOENT`), it sends the request to `legacySocketPath(socketPath)`, where hosts of older versions listen, if `isOwnLegacySocket` accepts that path. Otherwise it throws the root's `STORAGE_WRITE_ERROR` or the missing socket's error. Transport and response errors are `CliError` values (class from `src/cli/errors.ts`). An aborted `signal` rejects with the error from `makeAbortError`: the signal's `reason` when it is an `Error`, else a plain `Error` named `AbortError`. A failed `invariant` throws an `AssertionError`. [rpcClient.ts:sendRpc] [src/util/abort.ts:makeAbortError]

Methods: `getBackend`, `withBackend(rendererName, profile, loadReplayInput, operation, onProgress?)` (replays to a `ReplayInput` when the input is non-null, including an empty one at `targetSeq` -1, then runs the operation, and calls `onProgress` once the backend has booted and after each call of `replayTo`, also for a replay of another call that this one waits for), `screenshotPath`, `dispose`, `isBooted`, `isBootInFlight`, `getCurrentRendererName` and `getCurrentProfileName`. [renderer.ts:HostRendererManager]

[runCompletionCoordinator.ts:RunCompletionCoordinator] [runCompletionCoordinator.ts:RunCompletionEventAppender] [runCompletionCoordinator.ts:TimedRunCompletionWaitResult]

## Invariants

- `EventLog.open` derives the next `seq` from the last record (0 for an empty file), using `assertEventLogSize` and `parseEventLogContent` from `src/storage/eventLogCodec.ts`. `options.maxBytes` sets the size limit of the file. It defaults to `MAX_EVENT_LOG_SIZE`, must exceed `EVENT_LOG_TAIL_RESERVE_BYTES` and cannot exceed `MAX_EVENT_LOG_SIZE`, so the writer never passes what readers accept. `options.maxEntries` sets the limit of the number of events. It defaults to `MAX_EVENT_BUFFER_ENTRIES`, must exceed `EVENT_LOG_TAIL_RESERVE_ENTRIES` and cannot exceed `MAX_EVENT_BUFFER_ENTRIES`. Tests inject small limits. `append` asserts that the new `seq` equals the buffer length and validates the record with `EventRecordSchema`, so sequence numbers stay contiguous. A log that already holds its stop `marker` (a label that starts with `EVENT_LOG_LIMIT_LABEL_PREFIX`) starts stopped, so a reopened log stores only the `exit` record and writes no second stop record. A file of blank lines holds no record. When its size leaves less than `EVENT_LOG_TAIL_RESERVE_BYTES` free under `maxBytes`, `open` throws, because a stop record might not fit and a dropped append would have no earlier `seq` to report. [eventLog.ts:EventLog] [eventLog.ts:EventLogOptions] [eventLog.ts:EVENT_LOG_LIMIT_LABEL_PREFIX] [eventLog.ts:EVENT_LOG_TAIL_RESERVE_BYTES]
- At either limit, the file size or the number of events, `EventLog.append` stops the log. Ordinary records may fill the file up to `maxBytes` minus `EVENT_LOG_TAIL_RESERVE_BYTES`, and the buffer up to `maxEntries` minus `EVENT_LOG_TAIL_RESERVE_ENTRIES` (one entry for the stop record and one for the `exit` record). The first record that does not fit makes the log append one `marker` record with the label `agent-tty: event log limit reached (<limit>); later events are not recorded`, inside the reserves. `<limit>` is `<maxBytes> bytes` when the file size stopped the log and `<maxEntries> events` when the event count stopped it, so a reader can tell the two apart. A record that passes both limits is reported as the byte limit. From then on the log stores only the `exit` record, which also fits in the reserves, so the file never passes the byte limit and the buffer never passes the entry limit, and the host does not die from either. A record that the log does not store takes no `seq`. `append` resolves with the `seq` of the last stored record, and `startAppend` returns it as `seq`. Handlers, waited runs and `resize` therefore keep working, and the program keeps running. Its later output, input, resizes, signals and markers are in no snapshot, screenshot or export, because those replay the log. Every live feature that replays the log sees the program as it was at the stop: a live `wait` for text that appears after the stop times out, `wait --screen-stable-ms` can report a stable screen while the program keeps printing, and a mouse request after the stop encodes against the mouse modes that the stored log shows, not against modes that the program enabled or disabled after the stop (`reported` is false when the stored modes have mouse tracking off). `wait --idle-ms` and `wait --exit` follow the live program and are not affected. Once a write has failed, a dropped append rejects like any other. [eventLog.ts:EventLog] [eventLog.ts:EVENT_LOG_TAIL_RESERVE_BYTES] [eventLog.ts:EVENT_LOG_TAIL_RESERVE_ENTRIES] [mouseRpc.ts:createMouseRpcHandler]
- `EventLog.append` validates each payload with a strict Zod schema for its event type. It throws after `close()` and after an earlier write failed (the write queue stays rejected). It does not throw at a size limit or at `MAX_EVENT_BUFFER_ENTRIES`: the log stops instead. A failed write removes the failed records from the buffer. [eventLog.ts:EventLog]
- `SessionState` enforces its transitions: `setChildPid` and `setDimensions` need status `running`, and the child PID is set once. `SessionState` has no method that sets `hostPid`. `requestDestroy` moves `running`, `exited` or `failed` to `destroying`. `recordDestroyed` needs `destroying`. `recordExit` needs `running` or `exiting` and no earlier exit. [sessionState.ts:SessionState]
- `runHost` asserts that the manifest `sessionId` matches its argument and that the manifest `hostPid` equals its own `process.pid`. `waitForManifestFromCreate` asserts that `creatorPid` is a positive integer. [hostMain.ts:runHost] [hostMain.ts:waitForManifestFromCreate]
- The function from `createSerialManifestWriter` starts each write after the previous write settles. Each write takes the snapshot when it starts, not when it was requested. A failed write rejects only its own caller, and the next write still runs. [manifestWriter.ts:createSerialManifestWriter]
- The `inspect` handler reports the renderer backend, profile and boot state of the render manager, or of the mouse manager while the render manager has no backend. [hostMain.ts:runHost]
- These RPC handlers call `assertSessionCommandable` first: `type`, `mark`, `paste`, `run`, `sendKeys`, `mouse`, `resize`, `signal`, and `wait` in idle mode. [hostMain.ts:runHost]
- The `mouse` handler throws `CAPABILITY_UNAVAILABLE` before it takes the renderer lock when the renderer is not `libghostty-vt` or the cached `probeLibghosttyVt` result has no mouse encoder. Inside the lock it replays until the backend holds the whole event log, then stages held buttons, encodes, writes to the PTY and calls `EventLog.append`, which takes the `seq` synchronously, with no `await` in between. So the encoder sees every mode change in the log, and the log orders mouse input as the PTY received it. Only a `RangeError` or `TypeError` from `encodeMouse`, such as a cell outside the grid, becomes `INVALID_INPUT`. [mouseRpc.ts:createMouseRpcHandler]
- The `signal` handler accepts only `SIGTERM`, `SIGINT`, `SIGKILL`, `SIGHUP`, `SIGUSR1` and `SIGUSR2`, and throws `INVALID_SIGNAL` for others. [hostMain.ts:runHost]
- The `run` handler waits 30,000 ms by default. The `wait` handler needs exactly one of `exit` or `idleMs`, else it throws `INVALID_DURATION`. `waitForRender` polls every `RENDER_WAIT_POLL_INTERVAL_MS` (200 ms, `src/renderWait/limits.ts`). [hostMain.ts:runHost]
- `runHost` handles PTY exit once. If the status is `destroying` it records `destroyed`, else `exited`. Shutdown runs once. [hostMain.ts:runHost]
- `destroySession` throws `SESSION_NOT_FOUND` when there is no manifest, or when the session directory is gone at its `destroyed` write, and `SESSION_ALREADY_DESTROYED` for a destroyed session. When it records `destroyed` itself, `recordDestroyed` first writes the empty `<sessionDir>/destroyed` marker with `writeDestroyMarker`. Before it records a terminal session as `destroyed`, it calls `stopProgramGroup` with the group from `readProvenProgramGroup`, so only a group with a token gets a signal, and it throws `HOST_TIMEOUT` while that group lives. A session already recorded `destroyed` with the unshared group gets no wait, because only a process that saw the group recorded it, after its wait. A running session gets the `destroy` RPC. With `force` it gets `SIGKILL` for the program's group and, only when `hostMatches` proves the host, for the host: on Linux `judgeHost` must return `alive`, elsewhere `/bin/ps` must show `_host <sessionId>`, and on Windows the host gets no signal. It polls every 100 ms for at most 50 attempts and throws `HOST_TIMEOUT` if the status is still not terminal. With `force`, when the read of `program.json` or the first `isProgramGroupAlive` of the group throws an error that `isUnreadableGroupError` accepts (a `STORAGE_READ_ERROR` whose cause, or a `/proc` read whose code, is in `UNREADABLE_ERRNOS`), `stopUnlessUnreadable` waits `DESTROY_POLL_INTERVAL_MS` (100 ms, abortable) and reads and judges the group again. Only when that read throws such an error too does it stop and wait for the host alone, and `destroySession` records `destroyed` once the host has ended. An error after that first judgement, as in the wait, still throws. `forceSkipsGroup` runs that read and first judgement and returns whether such an error came, so `gcSessions` names `destroy --force` for a failed reconcile only then. [lifecycle.ts:destroySession] [programGroup.ts:isUnreadableGroupError] [programGroup.ts:forceSkipsGroup]
- `reconcileSession` writes `destroyed` (both PIDs `null`, the exit code kept, no failure fields) over a terminal manifest other than `destroyed` when the destroy marker exists (`writeMarkedDestroyed`). It then unlinks the socket, removes the Home's socket directory if it is empty, removes the old socket at `legacySocketPath` when `isOwnLegacySocket` accepts it, and returns. Otherwise it does nothing when the manifest is missing, the status is terminal or the host can be alive: `judgeHost` with the record from `host.json` does not return `dead`. A null `hostPid` counts as a dead host. `allocateSession` writes the host PID into the first manifest, so a new session already has a `hostPid`. After the liveness check, `reconcileSession` reads the manifest again and does nothing when it is now missing or terminal. Otherwise it maps the status it read again: `running` to `failed` (failure origin `host-death`), `exiting` to `exited`, `destroying` to `destroyed` and any other status to `failed` (origin `unknown`), and sets both PIDs to `null`. Right after that write, when its status was not `destroyed` and the destroy marker exists, it writes `destroyed` again from the same copy, with both PIDs `null` and no failure fields. When the session directory is gone at any of these writes, it returns. [lifecycle.ts:reconcileSession] [lifecycle.ts:writeMarkedDestroyed]
- Every kill of the program's process group goes through `stopProgramGroup`. For a record with a token, `judgeProgramGroup` returns `owned` only when a process that is not a zombie (a process whose main thread exited is not one while another of its threads runs) has the program's pid as its process group and session id, and the recorded autogroup on the recorded boot. A scan that finds no live member runs once more, because a member can fork and end after the scan listed `/proc`. `stopProgramGroup` reads that process again right before the kill. `unproven` (another boot id, or only members with another session id or autogroup) and `unknown` kill nothing. `gone` (no live member) sends the group SIGSTOP with `signalProcessGroup`, because a fork chain whose members each live about 2 ms is never in view, and a stopped member is. An `unknown` whose member without an autogroup still runs (`running`), and an `owned` whose witness ended before it was read again, do the same, because a member can end between two reads and a stopped member cannot. An `unknown` whose such members are all stopped, or whose boot id `/proc` refuses, gets no signal, so a group that job control stopped stays stopped. The judge then runs again, up to 5 times, and each such judgement sends SIGSTOP again, for a member that a SIGCONT from elsewhere resumed. When `/proc/self` does not name this process's pid, `/proc` belongs to another pid namespace and no SIGSTOP goes out. A frozen group that gets no kill gets SIGCONT, also when a scan throws. So a group id that an unrelated group took, whose members no scan shows either, gets a SIGSTOP and a SIGCONT. `unknown` means that `/proc` refused the boot id, or showed a member with the program's session id but no autogroup, so `isProgramGroupAlive` reads it alive. A record without a token gets the kill of its `pid`. A `{ childPid, sessionDirectory }` group gets the kill of `childPid`, and reads alive, only while `sessionDirectory` exists, checked in the same synchronous block. The unshared group `{ unshared: true }`, which a record with a token gives when `host.json` names another pid space, is missing or cannot be read (`readHostRecord` reads a failed read as missing), gets no signal and reads alive. [programGroup.ts:stopProgramGroup] [programGroup.ts:judgeProgramGroup]
- `captureProgram` records a token only on Linux, for its own child that leads its own session and has an autogroup other than the host's, within 250 ms, and only when `/proc` shows the boot id. `runHost` calls it right after `createPty` and writes the record before its first manifest write, with no `await` in between. [programGroup.ts:captureProgram] [hostMain.ts:runHost]
- `allocateSession` throws `INVALID_DIMENSIONS` for non-positive `cols` or `rows`, `STORAGE_READ_ERROR` when `cwd` is not a directory and `INVALID_INPUT` when the shell path is not a file. An empty `command` defaults to the shell path. It creates the session directory and calls `launch` only after these checks pass. [lifecycle.ts:allocateSession]
- `buildReplayInput` validates the manifest with `SessionRecordSchema` and requires its `sessionId` to match. It validates the events with `validateEventRecords` unless `trustValidated` is set. `targetSeq` is -1 for no events, else from 0 to the last `seq`. [replay.ts:buildReplayInput]
- `RpcServer.listen` removes a stale socket file (no answer within 1,000 ms, `ECONNREFUSED` or `ENOENT`) and throws when another server is listening. It asserts a socket path of at most 104 characters. [rpcServer.ts:RpcServer]
- `RpcServer` caps a request at 1,048,576 characters. `sendRpc` caps a response at `MAX_RPC_RESPONSE_CHARS` (67,108,864 characters, from `src/protocol/messages.ts`), so a structured snapshot with cells of a 500x200 screen (about 5.6 million characters when every cell is styled) fits. The server answers a success response above that cap with `PROTOCOL_ERROR` "RPC response takes N characters, over the 67108864-character limit.", with `responseChars` and `maxResponseChars` in `details`. `sendRpc` stops reading a response from an older host, which has no such check, at the cap and reports `PROTOCOL_ERROR` "RPC response is over the 67108864-character limit." with `maxResponseChars` in `details`. The server validates the request with `RpcRequestSchema`, the params and result with `RpcMethodSchemas`, and the response with `RpcResponseSchema` (all from `src/protocol/messages.ts`). A handler that throws a `CliError` gets an error response with its code, message and, when it has any, its `details`. It leaves `details` out when they do not serialize to a JSON object (a `BigInt`, a circular object, a `toJSON` that returns something else) or take more than 65,536 characters. It cuts an error message to 65,536 characters, without splitting a surrogate pair, and ends it with `[message truncated]`. A request id over 128 characters fails `RpcRequestSchema`, and the error response uses the id `unknown`. So an error response stays under 1,048,576 characters, which a CLI from before the larger response cap also reads, and keeps the error's code. `sendRpc` rebuilds that `CliError` with the same details. Any other thrown error becomes `RPC_ERROR` without details. If building or sending the response throws, the server logs the error and answers `RPC_ERROR` "RPC request handling failed unexpectedly.", so the host keeps running. Unknown methods get an error response. [rpcServer.ts:RpcServer] [rpcClient.ts:sendRpc]
- `sendRpc` waits 5,000 ms by default, as a socket inactivity timeout: each byte from the host starts the wait over. So a host that reports progress with `keepAlive` can take longer than 5,000 ms to answer, and a host that sends nothing for 5,000 ms ends in `HOST_TIMEOUT`. The `snapshot` command passes 60,000 ms when it asks for cells, because the host sends nothing while it builds every cell. `sendRpc` scans each response chunk once for the newline. It requires the response `id` to match the request. It maps `ECONNREFUSED`, `ENOENT` and `ECONNRESET` to `HOST_UNREACHABLE`, a socket timeout to `HOST_TIMEOUT` and other transport errors to `RPC_ERROR`. [rpcClient.ts:sendRpc]
- `HostRendererManager` runs backend operations one at a time. `withBackend` requires the replay input `sessionId` to match, and recreates the backend when the initial size changes. [renderer.ts:HostRendererManager]
- `withBackend` replays through `replayInSlices` when more than 32 events (`FIRST_SLICE_EVENTS`) are left. Each slice is a `replayTo` call with the events of the slice and the target of the whole replay, so a backend ends at the last event of the slice and does not rewind. The size of the next slice follows the time of the last one, aims at 500 ms (`TARGET_SLICE_MS`) and changes by at most four times. The last call gets the whole input, because a backend keeps its last input (the libghostty-vt screenshot replays it in a second renderer). `HostRendererManager` keeps the position that the last replay reported, and a backend that is further on, after a `mouse` request, makes the first slice skip its events. Any split of the events gives the same backend state. [replaySlices.ts:replayInSlices] [replaySlices.ts:nextSliceSize] [renderer.ts:HostRendererManager]
- The `snapshot`, `screenshot` and `run` handlers pass `MethodContext.keepAlive` to `withBackend` as `onProgress`, so a client waits for a replay that moves forward, also when the replay belongs to a request ahead of it in the queue. `keepAlive` is never called on a timer, so a renderer that hangs ends the client's wait with `HOST_TIMEOUT` 5 s after its last slice. A response line may start with spaces, which JSON allows and `sendRpc` of older versions parses. `waitForRender` and `mouse` pass nothing: a render wait answers at its own timeout, and `mouse` replays libghostty-vt only. The time of the boot and of one slice is still silent, and so is the second renderer of a libghostty-vt screenshot. [hostMain.ts:runHost] [rpcServer.ts:RpcServer]
- A waited `run` calls `EventLog.startAppend`, `registerWaitedRun` and `pty.write` with no `await` in between, then awaits `written`. When `registerWaitedRun` or `pty.write` throws, it waits for `written` to settle and rethrows that error, so a failed write never becomes an unhandled rejection. So no other input reaches the PTY or the log between the command's `seq` and its write, and the marker is registered before the command can print. [hostMain.ts:runHost]
- `RUN_MARKER_PATTERN` is `/^__AT_MARKER_([0-9a-f]{32})__$/u`. `registerWaitedRun` requires a unique marker and a non-negative integer `inputRunSeq`. `buildRunCompletePostamble` limits the postamble to 64 characters before its newline, and the postamble must not contain the marker. [runCompletionSentinel.ts:RUN_MARKER_PATTERN] [runCompletionCoordinator.ts:RunCompletionCoordinator] [runCompletionCoordinator.ts:buildRunCompletePostamble]
- A timed-out `wait` returns `{ kind: 'timeout' }`. An aborted `wait` rejects with an abort error. Both keep the sentinel registered, so the later completion bytes stay out of the output. [runCompletionCoordinator.ts:RunCompletionCoordinator]
- The `RunCompletionCoordinator` doc comment states that `ingestPtyData` and `flushPtyDataOnExit` must be called one at a time. [runCompletionCoordinator.ts:RunCompletionCoordinator]

## Side Effects

- `launchHost` runs `child_process.spawn(process.execPath, [...process.execArgv, process.argv[1], '_host', sessionId, String(process.pid)])` with `detached: true`, `stdio: 'ignore'` and an environment of the CLI's `process.env` merged with `config.env`, plus `AGENT_TTY_HOME` and `TERM`, then calls `unref()`. The last argument is the creator PID that the host passes to `waitForManifestFromCreate`. [lifecycle.ts:launchHost] [src/cli/main.ts:main]
- `allocateSession` calls `ensureHome`, creates the session directory with mode `0o700`, calls `launch` (in `create`, this starts the host process), writes `host.json` for that host with `captureHost` and `writeHostRecord`, and then writes `session.json` with `writeManifest` (`src/storage/manifests.ts`). It calls `ensureHome` before it checks `cwd`, because the `cwd` can be a new Home. It checks `cwd`, the shell path and the command segments before it creates the session directory, so a failed check leaves no session directory. A `chmod` failure after `mkdir` leaves an empty session directory under `<home>/sessions`. [lifecycle.ts:allocateSession]
- `destroySession` and `reconcileSession` call `process.kill` (signal 0 as a liveness probe, `SIGKILL` to stop, `SIGSTOP` and `SIGCONT` to freeze a group that no scan shows), read `program.json` and `host.json`, read `/proc/<hostPid>/stat` and the boot id on Linux, run `/bin/ps -o command=` before a host kill off Linux, write the manifest with `writeManifest`, unlink the socket file and call `removeSocketDirectoryIfEmpty`. `destroySession` also calls `sendRpc(..., 'destroy')` and writes the destroy marker with `writeDestroyMarker`, and `reconcileSession` checks whether that marker exists with `existsSync`. [lifecycle.ts:destroySession] [lifecycle.ts:reconcileSession]
- `listSessions` reads `<home>/sessions` and each manifest, and can call `reconcileSession`. [lifecycle.ts:listSessions]
- `stopProgramGroup` and `isProgramGroupAlive` read, without yielding, `/proc/<pid>/stat` of every process, `/proc/<pid>/task/<tid>/stat` of each process that shows Z, `/proc/<pid>/autogroup` of the group's members and `/proc/sys/kernel/random/boot_id`. `captureProgram` reads the same files for the program and the host. `writeProgramRecord` writes `<sessionDir>/program.json` through `writeValidatedJsonFileSync` (`src/storage/manifests.ts`), which creates no folder. `runHost` writes `<sessionDir>/host.json` the same way with `writeHostRecord`, right after it read its manifest. [programGroup.ts:stopProgramGroup] [programGroup.ts:captureProgram] [programGroup.ts:writeProgramRecord] [hostRecord.ts:writeHostRecord]
- `runHost` spawns the PTY with `createPty` (`src/pty/createPty.ts`), writes input to it, resizes it and kills it on idle timeout and shutdown. It writes `TerminalQueryResponder` replies to the PTY without logging them. [hostMain.ts:runHost]
- `runHost` polls `session.json` with `readManifestIfExists` and probes the creator process with `isProcessAlive` until the manifest appears or the creator exits. It writes `session.json` through `createSerialManifestWriter`, creates the socket directory with mode `0o700` and listens with `RpcServer` through `listenInSocketDirectory` and writes snapshot and screenshot artifacts through `src/snapshot/capture.ts` and `src/screenshot/capture.ts`. [hostMain.ts:runHost]
- `runHost` registers a `process.on('SIGTERM')` handler that starts shutdown, sends signals to the child with `process.kill` and starts `setInterval` timers for idle and wait polling. [hostMain.ts:runHost]
- `runHost` checks for the `create-failed` marker with `existsSync` before it spawns the program, and returns when it finds it. It checks again right after its start-up manifest write, before it listens, and then shuts down. From there on, `watchCreateFailed` checks for the marker every `CREATE_FAILED_POLL_INTERVAL_MS` (100 ms) while the creator process lives and once after it exited (off Windows, a `process.ppid` other than the creator's pid means that the creator exited; on Windows, a liveness probe that throws counts as exited; the watch stops after `CREATE_FAILED_WATCH_MAX_MS`, 60 s, in any case), and starts the shutdown when it finds the marker. [hostMain.ts:runHost]
- `runHost` rethrows a PTY-ingestion, event-log append, exit-handling or shutdown error in `process.nextTick`. The uncaught exception crashes the host process. [hostMain.ts:rethrowAsync]
- `resolveHostRendererName` reads `process.env.AGENT_TTY_HOST_RENDERER` and `process.env.AGENT_TTY_RENDERER`. [hostMain.ts:resolveHostRendererName]
- `EventLog.open` opens the file in append mode and runs `chmod 0o600`. `append` writes with `fileHandle.appendFile`, one call at a time, and never takes the file past its size limit. `close` calls `fileHandle.sync()` and then closes the file. [eventLog.ts:EventLog]
- `RpcServer.listen` uses `net.createServer`, listens on the socket path and runs `chmod 0o600` on the socket. `close` closes the server and unlinks the socket. [rpcServer.ts:RpcServer]
- `sendRpc` connects with `net.connect` and writes one JSON line. [rpcClient.ts:sendRpc]
- `HostRendererManager` boots, replays (in slices) and disposes backends from the injected factory. In `runHost` that factory is `createRendererBackend` (`src/renderer/registry.ts`), with the session's creation size as the libghostty-vt initial size. `screenshotPath` creates `<sessionDir>/screenshots` with `mkdirSync`. [renderer.ts:HostRendererManager]
- `RunCompletionCoordinator` uses `crypto.randomUUID` and `crypto.randomBytes`. It appends `output` and `run_complete` events only through its injected appender. [runCompletionCoordinator.ts:RunCompletionCoordinator]
- `createSerialManifestWriter` does I/O only through its `write` argument. [manifestWriter.ts:createSerialManifestWriter]
- `createMouseRpcHandler` does I/O only through its dependencies. `mouseInput.ts` does no I/O. [mouseRpc.ts:createMouseRpcHandler] [mouseInput.ts:prepareHeldMouseButtons]
- `runCompletionSentinel.ts`, `replay.ts` and `sessionState.ts` do no I/O. [runCompletionSentinel.ts:RunCompletionSentinelScanner] [replay.ts:buildReplayInput] [sessionState.ts:SessionState]
