# src/host

## Overview

`src/host` holds the per-session host and the CLI-side code that starts, reaches and cleans up hosts. `lifecycle.ts` allocates a session, spawns a detached host process and destroys, lists or reconciles sessions. `manifestWriter.ts` orders the host's manifest writes. `programGroup.ts` records the program's session token in `program.json` and decides before each kill of the program's process group whether the group is still the program's. `hostMain.ts` is the host process: it spawns the PTY, appends all ten event types (`output`, `input_text`, `input_paste`, `input_keys`, `input_run`, `run_complete`, `resize`, `signal`, `exit` and `marker`) to `events.jsonl` through `EventLog`, serves RPC on a Unix socket and renders through `HostRendererManager`. `runCompletionCoordinator.ts` and `runCompletionSentinel.ts` detect when a command sent with `run` has finished. The host is an internal detail. The CLI JSON envelope in `src/protocol/` is the stable surface.

## Interface

- `runHost(sessionId, creatorPid)` is the host process entry point. It waits for the first manifest with `waitForManifestFromCreate`, then registers RPC handlers for `inspect`, `snapshot`, `screenshot`, `type`, `mark`, `paste`, `run`, `sendKeys`, `resize`, `signal`, `wait`, `waitForRender` and `destroy`. [hostMain.ts:runHost]
- `waitForManifestFromCreate(path, creatorPid)` returns the manifest at `path`. It polls every 20 ms while the manifest is missing and the creator process is alive. When the creator exits before the manifest appears, it throws `SESSION_NOT_FOUND`. [hostMain.ts:waitForManifestFromCreate]
- `normalizeExitSignal(signal)` maps a PTY exit signal number to a string, or `null` for `null` and 0. [hostMain.ts:normalizeExitSignal]
- `isSessionCommandable(state)` and `assertSessionCommandable(state)` check that the session status is commandable. The assert throws `SESSION_NOT_RUNNING`. [hostMain.ts:isSessionCommandable] [hostMain.ts:assertSessionCommandable]
- `resolveHostRendererName(input?)` picks the renderer name from the input, then `AGENT_TTY_HOST_RENDERER`, then `AGENT_TTY_RENDERER`, then `DEFAULT_RENDERER_NAME` (from `src/renderer/names.ts`). It throws `INVALID_INPUT` for an unknown renderer name. [hostMain.ts:resolveHostRendererName]
- `MAX_CONSECUTIVE_POLL_FAILURES` (10) is the number of failed polls in a row after which a `waitForRender` wait ends as timed out. [hostMain.ts:MAX_CONSECUTIVE_POLL_FAILURES]
- `allocateSession(config, launch)` validates an `AllocateConfig`, creates the session directory, calls `launch(sessionId)` and writes the first `running` manifest with the returned PID as `hostPid`. It returns an `AllocateResult` with `sessionId` and `sessionDirectory`. [lifecycle.ts:allocateSession] [lifecycle.ts:AllocateConfig] [lifecycle.ts:AllocateResult]
- `launchHost(config)` spawns the host process for a `LaunchHostConfig` and returns its PID. `create` calls it from the `launch` callback of `allocateSession`. [lifecycle.ts:launchHost] [lifecycle.ts:LaunchHostConfig] [src/cli/commands/create.ts:runCreateCommand]
- `isProcessAlive(pid)` returns `false` for `null` and for a PID that `process.kill(pid, 0)` reports as `ESRCH`, and `true` when the probe succeeds. It asserts a positive integer PID and rethrows other errors, such as `EPERM`. [lifecycle.ts:isProcessAlive]
- `destroySession(sessionId, force?, options?)` destroys a session and waits until its manifest shows a terminal status. `DestroySessionOptions` has an optional `AbortSignal`. [lifecycle.ts:destroySession] [lifecycle.ts:DestroySessionOptions]
- `listSessions(home, all?)` returns `SessionSummary[]`. It reconciles active sessions first and hides terminal sessions unless `all` is true. [lifecycle.ts:listSessions] [lifecycle.ts:SessionSummary]
- `reconcileSession(sessionDirectory)` moves a non-terminal session to a terminal status when its host process is gone. [lifecycle.ts:reconcileSession]
- `captureProgram(pid)` returns a `ProgramRecord` (`version`, `pid`, `bootId`, `autogroup`) for the program that the host just spawned, and `writeProgramRecord(sessionDirectory, record)` writes it to `program.json`. `bootId` is a string and `autogroup` a number, or both are `null`. [programGroup.ts:captureProgram] [programGroup.ts:writeProgramRecord]
- `readProgramGroup(sessionDirectory, childPid)` returns the `program.json` record when it has a token. Otherwise it returns a record without a token for `childPid`, or `null` when `childPid` is `null`. [programGroup.ts:readProgramGroup]
- `stopProgramGroup(group)` SIGKILLs the group when the record proves it, and `isProgramGroupAlive(group)` reports whether the group still holds a process that the kill would target. `judgeProgramGroup(record, bootId, rows)` is the pure decision: `owned`, `gone` or `unproven`. `parseProcStat` and `parseAutogroup` parse `/proc/<pid>/stat` and `/proc/<pid>/autogroup`. [programGroup.ts:stopProgramGroup] [programGroup.ts:isProgramGroupAlive] [programGroup.ts:judgeProgramGroup] [programGroup.ts:parseProcStat]
- `SessionState` holds the host's in-memory `SessionRecord` (type from `src/protocol/schemas.ts`). Methods: `snapshot`, `setChildPid`, `setDimensions`, `setFailureOrigin`, `requestDestroy`, `recordDestroyed` and `recordExit`. [sessionState.ts:SessionState]
- `createSerialManifestWriter(path, snapshot, write?)` returns a function that writes `snapshot()` to `path`. The default `write` is `writeManifest` (`src/storage/manifests.ts`). `runHost` sends every manifest write through one such function. [manifestWriter.ts:createSerialManifestWriter] [hostMain.ts:runHost]
- `EventLog` is the append-only JSONL event log with an in-memory buffer. Methods: `static open(filePath)`, `append(type, payload)` (returns the new `seq`), `getEvents`, `getEventsSince(afterSeq)`, `readAll` and `close`. [eventLog.ts:EventLog]
- `MAX_EVENT_BUFFER_ENTRIES` is 250,000. `statEventLogBytes(filePath)` returns the file size or `undefined` when the file does not exist. `countEventLogEntries(filePath)` counts non-blank lines. [eventLog.ts:MAX_EVENT_BUFFER_ENTRIES] [eventLog.ts:statEventLogBytes] [eventLog.ts:countEventLogEntries]
- `buildReplayInput(sessionId, manifest, events, ...)` builds a validated `ReplayInput` (type from `src/renderer/types.ts`) with the initial size and target sequence number. [replay.ts:buildReplayInput]
- `RpcServer(socketPath, handlers)` serves newline-delimited JSON RPC on a Unix socket, one request per connection, with `listen()` and `close()`. `MethodHandler` and `MethodContext` type the handlers. `MethodContext.signal` aborts when the client socket closes. [rpcServer.ts:RpcServer] [rpcServer.ts:MethodHandler] [rpcServer.ts:MethodContext]
- `sendRpc(socketPath, method, params?, timeoutMs?, signal?)` sends one request to a host and returns the validated result. Transport and response errors are `CliError` values (class from `src/cli/errors.ts`). An aborted `signal` rejects with the error from `makeAbortError`: the signal's `reason` when it is an `Error`, else a plain `Error` named `AbortError`. A failed `invariant` throws an `AssertionError`. [rpcClient.ts:sendRpc] [src/util/abort.ts:makeAbortError]
- `HostRendererManager` keeps one current renderer backend. It disposes and replaces that backend when the renderer name or profile changes. Methods: `getBackend`, `withBackend` (replays to a `ReplayInput` when the input is non-null and its `targetSeq` is at least 0, then runs the operation), `screenshotPath`, `dispose`, `isBooted`, `isBootInFlight`, `getCurrentRendererName` and `getCurrentProfileName`. [renderer.ts:HostRendererManager]
- `RunCompletionCoordinator(appender)` tracks waited runs. Methods: `prepareWaitedRun`, `registerWaitedRun` (returns the shell `postamble`, the `sentinel` and a single-use `wait(timeoutMs, options?)`), `ingestPtyData`, `flushPtyDataOnExit` and `resetForExit`. Related types: `RunCompletionEventAppender`, `PreparedWaitedRun`, `RegisteredWaitedRunCompletion`, `RunCompletionWaitOptions` and `TimedRunCompletionWaitResult` (`completed`, `exited` or `timeout`). [runCompletionCoordinator.ts:RunCompletionCoordinator] [runCompletionCoordinator.ts:RunCompletionEventAppender] [runCompletionCoordinator.ts:TimedRunCompletionWaitResult]
- `RunCompletionSentinelScanner` splits PTY output into `SentinelPiece` values (`output` or `run_complete`) by finding registered sentinel frames. `RunCompletionPostambleEchoSanitizer` removes the shell's echo of the injected postamble from the output. [runCompletionSentinel.ts:RunCompletionSentinelScanner] [runCompletionSentinel.ts:RunCompletionPostambleEchoSanitizer] [runCompletionSentinel.ts:SentinelPiece]
- `RUN_COMPLETE_SENTINEL_PREFIX`, `RUN_COMPLETE_SENTINEL_SUFFIX`, `RUN_MARKER_PATTERN`, `assertRunMarker`, `buildRunCompleteSentinel` and `buildRunCompleteSignalSentinel` define and build the sentinel frames and run markers. [runCompletionSentinel.ts:RUN_MARKER_PATTERN] [runCompletionSentinel.ts:buildRunCompleteSentinel] [runCompletionSentinel.ts:buildRunCompleteSignalSentinel]

## Invariants

- `EventLog.open` derives the next `seq` from the last record (0 for an empty file), using `assertEventLogSize` and `parseEventLogContent` from `src/storage/eventLogCodec.ts`. `append` asserts that the new `seq` equals the buffer length and validates the record with `EventRecordSchema`, so sequence numbers stay contiguous. [eventLog.ts:EventLog]
- `EventLog.append` validates each payload with a strict Zod schema for its event type. It throws when the buffer holds `MAX_EVENT_BUFFER_ENTRIES` records, after `close()`, and after an earlier write failed (the write queue stays rejected). A failed write removes the failed records from the buffer. [eventLog.ts:EventLog]
- `SessionState` enforces its transitions: `setChildPid` and `setDimensions` need status `running`, and the child PID is set once. `SessionState` has no method that sets `hostPid`. `requestDestroy` moves `running`, `exited` or `failed` to `destroying`. `recordDestroyed` needs `destroying`. `recordExit` needs `running` or `exiting` and no earlier exit. [sessionState.ts:SessionState]
- `runHost` asserts that the manifest `sessionId` matches its argument and that the manifest `hostPid` equals its own `process.pid`. `waitForManifestFromCreate` asserts that `creatorPid` is a positive integer. [hostMain.ts:runHost] [hostMain.ts:waitForManifestFromCreate]
- The function from `createSerialManifestWriter` starts each write after the previous write settles. Each write takes the snapshot when it starts, not when it was requested. A failed write rejects only its own caller, and the next write still runs. [manifestWriter.ts:createSerialManifestWriter]
- These RPC handlers call `assertSessionCommandable` first: `type`, `mark`, `paste`, `run`, `sendKeys`, `resize`, `signal`, and `wait` in idle mode. [hostMain.ts:runHost]
- The `signal` handler accepts only `SIGTERM`, `SIGINT`, `SIGKILL`, `SIGHUP`, `SIGUSR1` and `SIGUSR2`, and throws `INVALID_SIGNAL` for others. [hostMain.ts:runHost]
- The `run` handler waits 30,000 ms by default. The `wait` handler needs exactly one of `exit` or `idleMs`, else it throws `INVALID_DURATION`. `waitForRender` polls every 200 ms. [hostMain.ts:runHost]
- `runHost` handles PTY exit once. If the status is `destroying` it records `destroyed`, else `exited`. Shutdown runs once. [hostMain.ts:runHost]
- `destroySession` throws `SESSION_NOT_FOUND` when there is no manifest, or when the session directory is gone at its `destroyed` write, and `SESSION_ALREADY_DESTROYED` for a destroyed session. Before it records a terminal session as `destroyed`, it calls `stopProgramGroup` without a `childPid` fallback, so only a group with a token gets a signal, and it throws `HOST_TIMEOUT` while that group lives. A running session gets the `destroy` RPC, or `SIGKILL` with `force`. It polls every 100 ms for at most 50 attempts and throws `HOST_TIMEOUT` if the status is still not terminal. [lifecycle.ts:destroySession]
- `reconcileSession` does nothing when the manifest is missing, the status is terminal or the host PID is alive. A null `hostPid` counts as a dead host. `allocateSession` writes the host PID into the first manifest, so a new session already has a `hostPid`. After the liveness check, `reconcileSession` reads the manifest again and does nothing when it is now missing or terminal. Otherwise it maps the status it read again: `running` to `failed` (failure origin `host-death`), `exiting` to `exited`, `destroying` to `destroyed` and any other status to `failed` (origin `unknown`), and sets both PIDs to `null`. When the session directory is gone at that write, it returns. [lifecycle.ts:reconcileSession]
- Every kill of the program's process group goes through `stopProgramGroup`. For a record with a token, `judgeProgramGroup` returns `owned` only when a process that is not a zombie has the program's pid as its process group and session id, and the recorded autogroup on the recorded boot. `stopProgramGroup` reads that process again right before the kill. `gone` (no live member) and `unproven` kill nothing. A record without a token gets the kill of its `pid`. [programGroup.ts:stopProgramGroup] [programGroup.ts:judgeProgramGroup]
- `captureProgram` records a token only on Linux, for its own child that leads its own session and has an autogroup other than the host's, within 250 ms. `runHost` calls it right after `createPty` and writes the record before its first manifest write, with no `await` in between. [programGroup.ts:captureProgram] [hostMain.ts:runHost]
- `allocateSession` throws `INVALID_DIMENSIONS` for non-positive `cols` or `rows`, `STORAGE_READ_ERROR` when `cwd` is not a directory and `INVALID_INPUT` when the shell path is not a file. An empty `command` defaults to the shell path. It creates the session directory and calls `launch` only after these checks pass. [lifecycle.ts:allocateSession]
- `buildReplayInput` validates the manifest with `SessionRecordSchema` and requires its `sessionId` to match. It validates the events with `validateEventRecords` unless `trustValidated` is set. `targetSeq` is -1 for no events, else from 0 to the last `seq`. [replay.ts:buildReplayInput]
- `RpcServer.listen` removes a stale socket file (no answer within 1,000 ms, `ECONNREFUSED` or `ENOENT`) and throws when another server is listening. It asserts a socket path of at most 104 characters. [rpcServer.ts:RpcServer]
- `RpcServer` and `sendRpc` cap a message at 1,048,576 characters. The server validates the request with `RpcRequestSchema`, the params and result with `RpcMethodSchemas`, and the response with `RpcResponseSchema` (all from `src/protocol/messages.ts`). Unknown methods get an error response. [rpcServer.ts:RpcServer] [rpcClient.ts:sendRpc]
- `sendRpc` waits 5,000 ms by default. It requires the response `id` to match the request. It maps `ECONNREFUSED`, `ENOENT` and `ECONNRESET` to `HOST_UNREACHABLE`, a socket timeout to `HOST_TIMEOUT` and other transport errors to `RPC_ERROR`. [rpcClient.ts:sendRpc]
- `HostRendererManager` runs backend operations one at a time. `withBackend` requires the replay input `sessionId` to match, and recreates the backend when the initial size changes. [renderer.ts:HostRendererManager]
- `RUN_MARKER_PATTERN` is `/^__AT_MARKER_([0-9a-f]{32})__$/u`. `registerWaitedRun` requires a unique marker and a non-negative integer `inputRunSeq`. `buildRunCompletePostamble` limits the postamble to 64 characters before its newline, and the postamble must not contain the marker. [runCompletionSentinel.ts:RUN_MARKER_PATTERN] [runCompletionCoordinator.ts:RunCompletionCoordinator] [runCompletionCoordinator.ts:buildRunCompletePostamble]
- A timed-out `wait` returns `{ kind: 'timeout' }`. An aborted `wait` rejects with an abort error. Both keep the sentinel registered, so the later completion bytes stay out of the output. [runCompletionCoordinator.ts:RunCompletionCoordinator]
- The `RunCompletionCoordinator` doc comment states that `ingestPtyData` and `flushPtyDataOnExit` must be called one at a time. [runCompletionCoordinator.ts:RunCompletionCoordinator]

## Side Effects

- `launchHost` runs `child_process.spawn(process.execPath, [...process.execArgv, process.argv[1], '_host', sessionId, String(process.pid)])` with `detached: true`, `stdio: 'ignore'` and an environment of the CLI's `process.env` merged with `config.env`, plus `AGENT_TTY_HOME` and `TERM`, then calls `unref()`. The last argument is the creator PID that the host passes to `waitForManifestFromCreate`. [lifecycle.ts:launchHost] [src/cli/main.ts:main]
- `allocateSession` calls `ensureHome`, creates the session directory with mode `0o700`, calls `launch` (in `create`, this starts the host process) and then writes `session.json` with `writeManifest` (`src/storage/manifests.ts`). It calls `ensureHome` before it checks `cwd`, because the `cwd` can be a new Home. It checks `cwd`, the shell path and the command segments before it creates the session directory, so a failed check leaves no session directory. A `chmod` failure after `mkdir` leaves an empty session directory under `<home>/sessions`. [lifecycle.ts:allocateSession]
- `destroySession` and `reconcileSession` call `process.kill` (signal 0 as a liveness probe, `SIGKILL` to stop), read `program.json`, write the manifest with `writeManifest` and unlink the socket file. `destroySession` also calls `sendRpc(..., 'destroy')`. [lifecycle.ts:destroySession] [lifecycle.ts:reconcileSession]
- `listSessions` reads `<home>/sessions` and each manifest, and can call `reconcileSession`. [lifecycle.ts:listSessions]
- `stopProgramGroup` and `isProgramGroupAlive` read, without yielding, `/proc/<pid>/stat` of every process, `/proc/<pid>/autogroup` of the group's members and `/proc/sys/kernel/random/boot_id`. `captureProgram` reads the same files for the program and the host. `writeProgramRecord` writes `<sessionDir>/program.json` through `writeValidatedJsonFileSync` (`src/storage/manifests.ts`), which creates no folder. [programGroup.ts:stopProgramGroup] [programGroup.ts:captureProgram] [programGroup.ts:writeProgramRecord]
- `runHost` spawns the PTY with `createPty` (`src/pty/createPty.ts`), writes input to it, resizes it and kills it on idle timeout and shutdown. It writes `TerminalQueryResponder` replies to the PTY without logging them. [hostMain.ts:runHost]
- `runHost` polls `session.json` with `readManifestIfExists` and probes the creator process with `isProcessAlive` until the manifest appears or the creator exits. It writes `session.json` through `createSerialManifestWriter`, creates the socket directory with mode `0o700`, listens with `RpcServer` and writes snapshot and screenshot artifacts through `src/snapshot/capture.ts` and `src/screenshot/capture.ts`. [hostMain.ts:runHost]
- `runHost` registers a `process.on('SIGTERM')` handler that starts shutdown, sends signals to the child with `process.kill` and starts `setInterval` timers for idle and wait polling. [hostMain.ts:runHost]
- `runHost` rethrows a PTY-ingestion, event-log append, exit-handling or shutdown error in `process.nextTick`. The uncaught exception crashes the host process. [hostMain.ts:rethrowAsync]
- `resolveHostRendererName` reads `process.env.AGENT_TTY_HOST_RENDERER` and `process.env.AGENT_TTY_RENDERER`. [hostMain.ts:resolveHostRendererName]
- `EventLog.open` opens the file in append mode and runs `chmod 0o600`. `append` writes with `fileHandle.appendFile`, one call at a time. `close` calls `fileHandle.sync()` and then closes the file. [eventLog.ts:EventLog]
- `RpcServer.listen` uses `net.createServer`, listens on the socket path and runs `chmod 0o600` on the socket. `close` closes the server and unlinks the socket. [rpcServer.ts:RpcServer]
- `sendRpc` connects with `net.connect` and writes one JSON line. [rpcClient.ts:sendRpc]
- `HostRendererManager` boots, replays and disposes backends from the injected factory. In `runHost` that factory is `createRendererBackend` (`src/renderer/registry.ts`). `screenshotPath` creates `<sessionDir>/screenshots` with `mkdirSync`. [renderer.ts:HostRendererManager]
- `RunCompletionCoordinator` uses `crypto.randomUUID` and `crypto.randomBytes`. It appends `output` and `run_complete` events only through its injected appender. [runCompletionCoordinator.ts:RunCompletionCoordinator]
- `createSerialManifestWriter` does I/O only through its `write` argument. [manifestWriter.ts:createSerialManifestWriter]
- `runCompletionSentinel.ts`, `replay.ts` and `sessionState.ts` do no I/O. [runCompletionSentinel.ts:RunCompletionSentinelScanner] [replay.ts:buildReplayInput] [sessionState.ts:SessionState]
